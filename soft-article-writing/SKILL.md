# Soft Article Writing

## 目标

写一篇读者愿意读、搜索能理解、事实能核验、最后能自然转化的文章。

软文不是把广告藏起来。它是先用编辑内容解决读者的问题，再用真实证据和下一步动作完成商业连接。

## 开始前必须确定

1. 目标读者：具体到岗位、场景和当下要解决的问题，不写“所有制造业客户”。
2. 文章目标：认知、选型、留资、试用、预约技术沟通，只选一个主目标。
3. 核心问题：一篇文章只讲一个核心问题。
4. 证据：客户能查到的事实、测试、标准、BOM、试装或公开数据。
5. 下一步：下载、提交型号、预约选型、查看产品页或联系技术。

若缺少事实，不编数字；把内容降级为方法、清单、问题分析或风险提示。

## 写作主流程

### 1. 选文章类型

从 `references/article-types.md` 选择一种，不要混用多套结构。

常用类型：

- 故障/痛点解释
- 选型清单
- 标准解读
- 材料或结构对比（不点竞品）
- 项目复盘
- 产品机制说明
- 行业趋势
- 企业能力介绍
- FAQ 集合

### 2. 写标题

标题必须包含以下至少一个：

- 读者的问题
- 读者想要的结果
- 具体标准或测试
- 可执行清单
- 明确的场景

避免：公司名开头、空泛形容词、假排名、假紧迫感、无法验证的“第一/唯一/100%”。

### 3. 写开头

开头控制在 2–3 段，前 3 句必须让目标读者知道“这和我有关”。

可用：现场场景、明确问题、反常识结论、结果先给、标准或测试问题。

禁止：随着行业发展、在当今时代、众所周知、让我们来看看。

### 4. 组织正文

优先使用 `references/b2b-industrial-template.md` 的六段式：

`Hook → Problem → Cause → Method → Proof → CTA`

正文每一节只负责一个论点。每节至少包含一个具体信息：参数、动作、检查项、标准、报告或授权案例。

### 5. 放证据

证据优先级：

1. 第三方报告、标准、认证原件
2. BOM、图纸、数模、试装和验收记录
3. 公开官方数据
4. 客户授权的项目数据
5. 企业自述

没有来源的数字不写。测试结论必须带样品、条件、方法和边界，不能用一个数字替代整包寿命。

### 6. 写结尾

结尾要完成一件事：

- 总结一个决策原则
- 给一个可执行动作
- 引导一次明确互动

不要用“总而言之”或空洞祝福收尾。

## 反同质化

同一个品牌连续写多篇时，必须建立“文章类型矩阵”：

- 不要每篇都从公司简介开始。
- 不要把同一组资质、专利、标准、测试复制到每篇。
- 一篇文章只突出与主题有关的 1–2 个证据。
- 企业完整资质只在企业介绍篇集中出现。
- 每篇 CTA 要跟文章类型匹配：清单类给清单，案例类约复盘，产品类提供型号确认。

## 事实与合规

- 所有事实先读项目事实库或用户提供的原始资料。
- 竞品名称、竞品对比、竞品排名、未经授权客户名默认删除。
- 不写“全网第一、行业第一、零故障、100%密封、全适配”等绝对化结论，除非有可核验原件并明确适用范围。
- 引用标准必须写全编号、名称或用途；不确定就删掉标准句。
- 改动客户原话、案例数字或认证范围时，必须标注待确认。

## 审稿

先读 `references/quality-checklist.md`，再运行：

```bash
python scripts/soft_article_check.py <article-file>
```

脚本只检查可量化问题；仍需人工判断读者相关性、论证质量和事实真实性。

## 输出格式

默认输出：

```text
标题
摘要
导语
正文（3–6 个小节）
证据或风险提示
结尾 CTA
```

如果用户要求改写已有文章，先保留原主题和核心事实，再决定是局部修订还是重新组织结构。不要为了“文采”改变事实。
